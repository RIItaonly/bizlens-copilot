# 数据与合规

系统跑在一套完全合成的数据上。这份文档说明数据怎么来的、为什么不用真实数据，以及口径和权限是怎么管的。

## 1. 数据来源

`data/seed/` 下 7 张表由 `scripts/gen_seed.py` 生成，随机种子固定为 `20251103`：

| 表 | 内容 | 行数 |
|---|---|---|
| `project.csv` | 项目主数据（编码、名称、区域、状态、合同额） | 30 |
| `contract.csv` | 合同（签约期、金额、首付款比例、状态） | 41 |
| `revenue.csv` | 每项目每期确认收入、开票、回款 | 110 |
| `cost.csv` | 每项目每期四类成本 | 440 |
| `plan.csv` | 每项目每期计划收入 | 110 |
| `headcount.csv` | 区域期末人数 | 15 |
| `org.csv` | 区域与事业部 | 3 |

固定种子意味着任何人克隆仓库都能得到完全一样的数字，评测结果可复现。

## 2. 为什么不用真实数据

- 真实经营数据涉及客户、合同金额和人员，不能公开；
- 合成数据可以刻意构造边界样本：负毛利、零收入在建项目、首付款超限、回款率触线；
- 评测需要 ground truth，合成数据可以精确计算。

代价是数据分布不真实。脏数据、缺报量、口径漂移这些真实问题，合成数据模拟不出来。所以这里的评测只能证明链路通、逻辑对，不能证明在客户数据上同样有效。

## 3. 口径治理

`data/metrics.yaml` 是唯一事实来源，9 个指标都在这里定义：公式、粒度、维度、边界情况、负责人、版本。

三条约束：

1. 代码里不出现第二份指标定义，聚合表达式集中在 `src/semantics/layer.py` 的 `EXPR`；
2. 口径冲突要留决策记录（`conflicts_resolved`），写清选择和代价；
3. 改口径必须升版本，历史数据不追溯重算。

## 4. 权限与审计

设计上按企业系统的要求做，当前实现只覆盖了最小集：

| 机制 | 设计 | 当前实现 |
|---|---|---|
| 行级权限 | 查询层按区域/项目过滤，不依赖提示词 | 已支持区域过滤 |
| 只读 | 业务库只给读权限 | SQLite 内存库，天然只读 |
| 留痕 | 提问、工具调用、结果、审批意见全记录 | 记录 SQL 与引用 |
| 人工审批 | 低置信度、高金额、跨期调整强制人审 | 报告模板中预留审批段 |

## 5. 边界

- 不做预测和预算编制，数据量与责任边界都不支持；
- 不做自动写回业务系统，分析错了可以改，改错业务数据要赔钱；
- 不提供法律或审计意见，合同审核场景只做辅助。
