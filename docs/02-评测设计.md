# 评测设计：怎么证明这个东西真的有用

> 真正稀缺的是"能定义什么叫做好了，并跑出数"。
> 本文是 BizLens 的评测规范，可直接复用到其他企业 AI 项目。

## 1. 为什么评测要单独拿出来讲

企业客户不会因为 Demo 流畅就买单，他们问的是：

- 100 个真实问题里，它能答对几个？
- 答错的时候，是错得离谱，还是错得可接受？
- 我怎么知道下一版比这一版好？

没有评测集，这三个问题都答不了，项目就永远停在"演示"阶段。

## 2. 评测集结构

**60 条任务，6 类各 10 条**，全部基于合成数据构造。

| 类别 | 考察点 | 示例 |
|---|---|---|
| T1 单指标查询 | 指标映射、时间范围 | "华东区上季度收入多少？" |
| T2 对比与排名 | 多指标、排序、口径 | "利润率最低的 5 个项目" |
| T3 异常识别 | 阈值、同比环比 | "哪些项目成本超支超过 10%？" |
| T4 归因分析 | 贡献度拆解、证据链 | "A 项目毛利为什么下降？" |
| T5 制度问答 | 检索、引用准确 | "费用分摊的口径是怎么规定的？" |
| T6 报告生成 | 结构完整、建议可执行 | "生成 B 项目季度经营简报" |

**难度分层**：每类 10 条 = 4 简单 + 4 中等 + 2 困难。困难题允许系统回答"无法确定"，此时不算错，算"正确拒答"。

## 3. 单条任务的数据结构

```json
{
  "id": "T3-007",
  "category": "T3",
  "difficulty": "medium",
  "question": "哪些项目本季度毛利率低于 15%？",
  "ground_truth": {
    "answer_type": "table",
    "rows": [{"project": "P-102", "margin": 0.112}, {"project": "P-207", "margin": 0.134}],
    "must_cite": ["metric:项目毛利率", "table:project_finance"]
  },
  "rubric_overrides": {"数值正确性": 2},
  "notes": "需排除已结项项目"
}
```

`ground_truth` 由人工基于同一份合成数据算出，不由模型生成。

## 4. 评分规则（Rubric）

四个维度，每维 0/1/2 分，总分 8 分。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| **数值正确性** | 关键数字与基准不一致 | 部分一致，或口径有偏差 | 全部一致，口径正确 |
| **归因有效性** | 无依据 / 编造 | 有依据但只覆盖部分因素 | 有依据且覆盖主要因素 |
| **引用可追溯** | 无引用 | 有引用但页码/字段错 | 引用准确，可点回源头 |
| **可执行性** | 空泛套话 | 有动作但缺责任/时限 | 有动作、责任人、时限 |

**通过标准**：总分 ≥ 6 **且** 数值正确性 = 2。数值错的回答，写得再漂亮也不算通过。

## 5. 指标定义

| 指标 | 定义 | 目标 |
|---|---|---|
| 任务成功率 TSR | 通过任务数 / 总任务数 | ≥ 80% |
| 数值准确率 NAR | 对账一致的数字 / 总数字 | ≥ 95% |
| 引用命中率 CHR | 引用正确的任务 / 需引用的任务 | 100% |
| P95 时延 | 端到端 95 分位耗时 | ≤ 30s |
| 单任务成本 | token + 工具调用折算 | ≤ ¥0.5 |
| 人工修改率 | 1 − 草稿与终稿的文本相似度 | ≤ 20% |

人工修改率最容易被忽略，但它最接近真实体验：**改得越少，越说明可用**。

## 6. 防"自己出题自己满分"

这是评测最容易造假的地方，必须有机制：

1. **留出集（holdout）**：20% 任务不参与任何调优，只在最终评测时跑。
2. **双人标注**：至少 20% 任务由两人独立给出 ground truth，分歧要讨论到达成一致。
3. **盲评**：评分时不知道结果来自哪个版本。
4. **版本冻结**：评测集定版后加 tag，改题必须记录原因。
5. **失败案例不删**：失败任务永久保留，作为回归集。

## 7. 报告模板

```markdown
## 评测报告 v0.3（2026-xx-xx）

| 指标 | v0.2 | v0.3 | 变化 | 是否达标 |
|---|---|---|---|---|
| TSR | 68% | 81% | +13pt | 是 |
| NAR | 91% | 96% | +5pt | 是 |
| P95 时延 | 41s | 27s | −14s | 是 |
| 单任务成本 | ¥0.62 | ¥0.44 | −29% | 是 |

### 分类表现
| 类别 | 通过率 | 主要失败原因 |
|---|---|---|
| T3 异常识别 | 70% | 阈值边界判断错误 |
| T4 归因 | 60% | 只给了单一因素 |

### 本版改了什么
- 在查询层增加"已结项项目"默认过滤，修复 4 条 T3 失败
- 归因改为贡献度拆解，T4 通过率 +20pt

### 仍未解决
- T6 报告建议仍偏模板化，需引入"动作库"
```

## 8. 回归流程

```
改动 → 跑全量 60 条 → 对比上一版 → 分类看退化 → 定位失败 → 修复 → 再跑
```

规则：**任何一个类别通过率下降超过 5pt，不允许合入**，即使总分上升。

## 9. 落地成本

- 造 60 条任务：约 3 人天（含双人标注）
- 每轮全量评测：约 40 分钟机器时间 + 0.5 人天分析
- 这套东西一旦建成，后续每个版本都能复用，是团队资产而不只是项目资产

> 评测集的建设成本通常在第一次就付完了，后面边际成本很低。这也是为什么它值得在 POC 阶段就做。
